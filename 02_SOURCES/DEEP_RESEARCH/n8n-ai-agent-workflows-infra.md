# AI Agent Workflows and Infrastructure

Building robust AI-driven chat agents (for sales, contracts, etc.) requires careful design of workflows, memory/storage, and monitoring. A common pattern is to break large processes into smaller “micro-agents” or sub-workflows, each with a single clear objective. For example, one agent might *qualify leads*, another *schedule calls*, and another *handle closing* – rather than a single AI trying to do everything. This specialization keeps each prompt small and predictable.  In practice, each agent uses **structured output** to hand off to tools (like CRM updates) rather than having the AI itself manipulate the CRM. For instance, n8n documentation shows an AI agent formatting chat input into a JSON lead record (with fields like `email` and `description`), which a separate tool (sub-workflow) then writes to a database【34†L102-L110】. By offloading tasks like updating CRM fields or sending emails to explicit tool-nodes (or sub-workflows), the AI’s context window stays small and reliability improves.

A key n8n best practice is **using sub-workflows**. The n8n docs note that calling one workflow from another “allows you to build modular, microservice-like workflows” and “can help if your workflow grows large enough to encounter memory issues”【35†L1538-L1541】. In other words, if a flow has hundreds of nodes or processes large data batches, splitting it into sub-workflows (via the *Execute Sub-workflow* trigger/node) avoids hitting context or memory limits.  For example, if you need to process 1,000 records, you might spawn 10 sub-workflows of 100 each in parallel (instead of one giant loop), which is much faster and keeps each workflow lightweight. This is especially important when using an AI agent: each AI call adds prompt and response to the context. A shorter, focused flow means fewer chat messages and tool calls per agent. 

- **Heavy vs. Many**. Note that “large” workflows can mean *computationally heavy* (large databases or loops) or simply *many small steps*.  A workflow that loops over a 20K-row database is heavy even if it has few nodes, while a workflow with dozens of IF/Switch nodes is light per node. n8n’s sub-workflows help manage both cases: pull out repeatable tasks into separate flows, and parallelize heavy loops into batches.  
- **Structured Output & Tools**. Always have the AI produce a clear, structured response (JSON or key/value pairs) when you need to act on data. Then use n8n “Tool” nodes or simple code nodes to parse that output and perform updates. (This keeps the AI from making unintended changes.)  For example, an agent can output `{"status": "Qualified", "next_step": "Schedule Demo"}`, and your workflow code can take that and call the CRM API to update the lead status. This avoids the AI having to “know” your CRM schema in full. 

By designing agents this way, each agent’s prompt stays focused and the *window of context* remains manageable. Remember that LLMs have finite context lengths (e.g. 8K–32K tokens for GPT-4), so loading hundreds of prior messages or a huge product catalog into the prompt will overflow it. Instead, use **Retrieval-Augmented Generation (RAG)** when needed: store large or volatile information externally and fetch it on demand. RAG lets the AI query a knowledge base or database for facts rather than storing all in the chat. For example, static policies or a product manual can live in a vector store or document, while a query to the agent triggers a semantic search and returns the relevant snippet【10†L58-L66】. In practice, we only include in-context the “current” situation (e.g. which stage the lead is in), and leave things like full price lists or promotions out of the prompt. Instead, the workflow can fetch those (e.g. from a Google Doc or database) right when needed. 

## Data Stores and Memory

For **chat history and memory**, a reliable approach is to use a database per client. n8n’s AI integrations support **PostgreSQL chat memory**: it automatically creates a table (e.g. `n8n_chat_histories`) to store each message with a session ID【7†L55-L63】. In practice, one DB per customer or tenant (possibly with separate schemas) isolates data. This lets the AI “remember” past exchanges for context without losing it on restarts. We don’t use Redis or similar for full chat history: Redis is in-memory only (non-persistent) and better suited for ephemeral caches or as a simple key-value store. In other words, use Postgres for the conversation log (since it’s durable) and use Redis *only* for transient caching or leaderboards, not for your message archive. 

For RAG and vector search, many teams now use **PGVector** (a PostgreSQL extension) instead of a separate vector DB.  PGVector embeds the vectors as a column in your Postgres tables and supports HNSW indexes. The advantage is simplicity: one database to back up, monitor, and secure. A recent comparison notes that “PGVector adds vector search to the database you already have, keeping documents and embeddings in the same table. Qdrant is a standalone service… with a richer feature set for advanced filtering”【14†L28-L33】. In other words, PGVector is simpler (just run `CREATE EXTENSION vector;` and add a vector column) and is very fast for up to millions of vectors, while Qdrant shines only at huge scale. Another study found that with the right extensions “Postgres delivers competitive performance” for vector search compared to a specialized DB【13†L246-L254】. Thus, unless you have extremely high scale or special filtering needs, using PGVector in your same Postgres is usually sufficient.

## Monitoring & Production Readiness

When an AI-based workflow goes live, you need robust monitoring. The n8n platform provides tools for this. For example, you can use the **Error Trigger** node to catch any workflow failures in real time. An error workflow can run automatically whenever a main flow errors【19†L1537-L1540】. Inside that error handler you can log details, notify you, or even try a fallback. Additionally, n8n’s API lets you poll for failed executions: community templates exist that hourly query “get all failed executions in the last hour” and then send a Slack (or WhatsApp/email) alert【17†L83-L91】. For instance, one workflow fetches recent errors, groups them by workflow, and posts a summary to Slack so you can investigate immediately.

Beyond n8n, monitor the infrastructure: check container logs and the task queue. If the chatbot hung, inspect the worker and task runner components. Often failures are due to resource limits (e.g. many messages spiking memory), queue backups, or misconfigured webhooks. A common solution is simply **scale up** or redeploy: e.g. flush the n8n queue (restarting can clear it) and then watch if it recurs. If the client suddenly triples traffic, you should be notified so you can preemptively add resources. In short: set up alerts for high CPU/memory on your VPS, use uptime tools (UptimeRobot, Kuma, etc.) for service liveness, and leverage both n8n’s built-in error handling and custom alert workflows to notify you of failures.

## Chatwoot Integration

**Chatwoot** is an open-source customer messaging platform (like a free Intercom/Helpdesk) that we use to handle multi-channel conversations. It typically runs as Ruby on Rails with sidekiq workers, and requires PostgreSQL, Redis, an email service, and S3-compatible storage for media【23†L122-L131】. In production, you’d deploy Chatwoot servers (web + workers), configure Redis for caching/background jobs, and point it at a Postgres database. For integration with n8n, there is an n8n “Chatwoot” community node【21†L305-L312】. This node can send and receive messages via the Chatwoot API. For example, you can use the Chatwoot **Trigger** node to listen for new customer messages (it auto-registers a webhook in Chatwoot), then have your n8n workflow process that message (pass it to an AI agent, look up context, etc.) and reply by calling the Chatwoot “Send Message” action. In short, Chatwoot manages the customer-facing inbox (WhatsApp, Instagram, email, etc.) and n8n handles the logic. This separation is ideal: Chatwoot’s UI lets human agents jump in if needed, while n8n automates routine replies and CRM updates. (As noted in Chatwoot docs, you can deploy it via Docker or Kubernetes for easy scaling【23†L122-L131】.)

## Example Agents

Below are sketch designs for the requested agents:

- **Contract Analysis Agent**. This agent should *ingest* a contract (PDF or image) and extract key terms (dates, amounts, parties, clauses) as structured data. A proven pattern is retrieval-augmented parsing: first use OCR to get text, then chunk the document and let the AI reason over relevant parts. For example, OpenAI describes an internal “contract data agent” that **pulls only the relevant clauses into the prompt, parses them to JSON**, and flags any non-standard terms【25†L68-L77】【25†L80-L89】. We’d follow that: have a n8n sub-workflow that runs OCR (and maybe a vector search on known templates), then call an LLM with a prompt like “Extract the contract’s effective date, parties, term, and payment terms, listing any unusual clauses, in JSON.” The AI returns structured output. Finally, present that to a human for verification (perhaps via Chatwoot or email). This mirrors the OpenAI case: “heavy lifting happens with AI… then finance experts review the structured output”【25†L88-L97】. In practice, store the final output in a database or spreadsheet for reporting. Ensure the prompt includes citations or references (e.g. “according to clause 5, the service level is 99%”), so reviewers can trace it.

- **Technical Quoting (Budget) Agent**. This agent should process technical drawings (DWG/PDF) and output a bill of materials or quote. Modern AI tools can do this: for example, state-of-the-art AI agents now “extract annotations, dimensions, and material specs from scanned technical drawings with near-perfect reliability”【27†L68-L75】. We would set up a flow: first convert the DWG/PDF to images or text (using an OCR/CAD parser), then use an AI vision or multimodal agent to read labels and tables. The agent would output a structured BOM list (part codes, quantities). We might use a specialized API (some vendors offer CAD-to-data services) or a vision-LLM. Once the list is generated, we feed it back to the sales team (via Chatwoot or email) for review. To keep it efficient, only feed one page or segment into the AI at a time, and assemble results. The Energent.ai report suggests uploading batches of drawings to get tabular outputs – in our case, we’d do one plan at a time and append its items to a running list. Prices and dynamic factors should then be applied (possibly via a lookup table or RAG query) outside of the agent, to avoid huge prompt context. 

- **AI SDR Agent with Pipedrive**. This agent engages incoming leads (via Chatwoot) and updates Pipedrive CRM. Using n8n’s built-in Pipedrive nodes【32†L591-L598】, the agent can create or update a Contact, Lead, or Deal. For example, after qualifying a lead, the agent might output: `{"contact_name": "Alice", "status": "qualified", "notes": "Interested in X"}`, and the workflow calls the Pipedrive node “Create/Update Person” and “Create Deal” using that data.  We must clearly define the agent’s limits: perhaps one agent *qualifies* (asks discovery questions and updates Pipedrive with status), while another agent *schedules demos* (seeing if criteria met, then sending a calendar invite). The Pipedrive integration is straightforward – add the Pipedrive credential in n8n, then choose actions like “Create a deal” or “Update a person” from the node’s dropdown【32†L591-L598】. The LLM itself should not schedule or book; it should just output the intent and data (which n8n then executes via the Pipedrive node). This matches the best practice: AI decides *what* to do in terms of data (e.g. “Lead qualified, update status”), and the workflow does *how* to do it (API calls).

Throughout, remember to **isolate context**. Keep chat memory short (e.g. just the current conversation), use Postgres for long-term logs【7†L55-L63】, and use tools/RAG for everything else. Use error-handling subflows to catch glitches and notify you instantly【19†L1537-L1540】【17†L83-L91】. By following these patterns – modular workflows, clear tool handoffs, appropriate databases, and vigilant monitoring – your AI agents and n8n automations will be reliable, scalable, and maintainable.
